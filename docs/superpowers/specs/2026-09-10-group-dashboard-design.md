# Локальный дэшборд групп SolutionRunner

## Цель

Сделать лёгкий локальный канбан для работы с группами SolutionRunner. Доска
должна автоматически видеть уже зарегистрированные и ранее обработанные
группы, показывать проверяемые технические состояния и давать отдельное место
для ручной работы: колонки, комментарии, ссылка на Codex-задачу и визуальная
проверка результата.

Plane для этой задачи слишком велик. За визуальную основу берётся MIT-проект
OpenKanban, но только его компактная Preact-доска. Cloudflare Wrangler, D1 и
исходный backend не переносятся.

## Архитектура

Дэшборд живёт в том же репозитории и checkout, без worktree:

```text
dashboard/                         Preact + JavaScript + Vite
config/catalogs.json               UUID и понятные названия каталогов
src/solution_runner/dashboard/     локальная Python API
var/dashboard/dashboard.sqlite3    ручное состояние доски
var/dashboard/previews/            кэш загруженных превью
```

Python API использует стандартные `http.server`, `sqlite3`, `json` и
`pathlib`; новый веб-фреймворк не добавляется. Один процесс раздаёт собранный
фронтенд и `/api/*`. В режиме разработки Vite проксирует `/api` в тот же
Python-процесс.

### Инициализация группы

Новая карточка сначала попадает в колонку `Инициализация`. На этом этапе
backend один раз читает через MCP структуру исходной группы и сохраняет в
SQLite локальный индекс:

- UUID каталога, source group ID и локальный ключ группы;
- problem ID и source problem ID родителя;
- problem ID, source problem ID и порядок каждого ребёнка;
- наличие секций условия, решения и ответа;
- для каждого ассета — ID, секцию, asset key и тип PNG/SVG.

Индекс не является копией `normalized_content` и не содержит плана будущих
преобразований. Актуальный текст агент и раннер читают через MCP по сохранённым
ID только тогда, когда он нужен. После успешной инициализации карточка переходит
в `На регистрацию`; ошибка остаётся внутри `Инициализации` с диагностикой.

Обычный dry-run и apply не повторяют inventory группы. Общий launcher получает
готовый локальный состав задач из SQLite и работает строго по нему. Если
сохранённый ID исчез, сменил группу или перестал разрешаться через MCP, запуск
завершается явной ошибкой. Автоматической переинициализации нет: обновление
индекса — отдельное явное действие.

## Источники данных и бэкфилл

При старте и по явной команде синхронизации backend строит объединённый список:

1. `all_group_profiles()` — все текущие зарегистрированные группы;
2. `var/**/runs/*/summary.json` — группы, для которых уже были запуски;
3. соседние `apply-results.json` и `helpers-results.json` — применение,
   Helpers и локальные ошибки.

Ключ группы берётся из `summary.json`, а не разбирается из имени каталога.
Для нескольких запусков используется самый новый корректный отчёт. Повреждённый
отчёт пропускается и отображается как диагностическое предупреждение, не
ломая весь бэкфилл.

Группа из истории сохраняется на доске, даже если её больше нет в текущем
реестре. Такая карточка получает отметку `legacy`.

Технические факты не редактируются вручную:

- `registered` — группа присутствует в реестре;
- `run` — найден корректный отчёт запуска;
- `applied`, `already_complete`, `blocked`, `failed` — счётчики из применения;
- `helpers_applied`, `helpers_failed`, `helpers_skipped` — счётчики Helpers;
- `helpers_ready` — все требуемые Helpers завершены без ошибок.

SQLite хранит локальный индекс, собранный на этапе `Инициализация`, и ручную
надстройку: колонку, комментарии, ссылку на Codex-задачу, запрос на доработку и
контракт обработки группы. В контракт входят
политики существующего решения и картинок, проверки ответа и Helpers, а также
выборка от одной до трёх задач для просмотра агентом. Повторный бэкфилл
обновляет факты, но не затирает эту надстройку.

При первом появлении карточки её начальная колонка определяется фактами:

- индекс группы ещё не собран — `Инициализация`;
- индекс собран, но обработчик не зарегистрирован — `На регистрацию`;
- нет запуска — `На регистрацию`, если группа не зарегистрирована,
  иначе `В работе`;
- есть ошибки или блокировки — `Проблемы`;
- есть запуск без подтверждённого применения — `Проверка`;
- применение завершено, но Helpers не готовы — `В работе`;
- Helpers готовы — `Готово`.

После первого импорта перемещение карточки меняет только ручную колонку.

## Интерфейс

Основной экран — обычный горизонтальный канбан с шестью колонками:
`Инициализация`, `На регистрацию`, `В работе`, `Проверка`, `Проблемы`, `Готово`.
Карточка показывает название или ключ группы, понятное название каталога и
компактные технические счётчики. Отдельный справочник `config/catalogs.json`
связывает стабильный UUID каталога с его названием из TeacherHelper. В фильтре
показываются название и полный UUID.

При добавлении пользователь указывает ключ группы и вводит UUID каталога.
Известные UUID показаны рядом как быстрые варианты, но не ограничивают ввод,
оставляет комментарий агенту и при необходимости меняет контракт обработки.
Название и путь пользователь не вводит. Карточка появляется в `Инициализации`,
а backend заполняет известную структуру группы и её локальный индекс. Агент
подключается только после перехода в `На регистрацию`.
По умолчанию существующее решение сохраняется, картинки выбираются
автоматически, проверки ответа и Helpers включены, а агент смотрит одного
ребёнка. Пользователь всегда видит одно итоговое превью.

Открытая карточка не превращается в маленькую форму. Справа появляется широкая
панель примерно на три четверти окна, а доска остаётся видна слева.

В панели:

1. закреплённый заголовок: путь группы, технические отметки и Codex-задача;
2. вкладка `Проверка` по умолчанию: сохранённый `normalized_content` и локальный
   результат dry-run для одной и той же задачи рядом; дополнительные проверочные задачи добавляются по явному
   нажатию и переключаются внутри той же карточки;
3. вкладки `Все задачи`, `Прогон`, `Проблемы`, `История`;
4. поле локального комментария;
5. зона действий для одной задачи, группы и Helpers.

Комментарий, оставленный в колонке `На проверке`, автоматически возвращает
карточку в `В работе` и ставит отметку `Ждёт агента`. Сам комментарий остаётся
в SQLite; отправка в Codex-задачу будет отдельной интеграцией.

Вкладка `Все задачи` показывает тот же локальный индекс группы, а не создаёт
второй список. Одна строка соответствует одной задаче и содержит: source problem
ID, наличие условия/решения/ответа, PNG/SVG-ассеты по секциям, последний статус
dry-run, apply и Helpers, а также итог `готово`, `пропущено` или `ошибка` с
причиной. Фильтры: `Все`, `Готово`, `Пропущено`, `Ошибки`. Нажатие строки
открывает превью выбранной задачи; комментарий остаётся единым для группы.
Результаты этапов хранятся отдельно от инвентарных строк, поэтому явная
переинициализация не стирает историю обработки сохранившихся problem ID.

Превью использует реальный HTML карточки TeacherHelper, публичные ссылки на её
ассеты и KaTeX для LaTeX. Данные не загружаются автоматически при старте доски.
Превью никогда не читает parser output. Левая сторона — сохранённый снимок
`normalized_content` перед тестовым прогоном, правая — результат локального
наложения transformations из dry-run на тот же снимок. MCP-записей на этом
этапе нет. Снимок хранится в `var/dashboard/previews/`; если актуального dry-run
нет, интерфейс не подменяет его историческими или моковыми данными. Ответ
показывается компактно в одной строке. Комментарий относится ко всей группе,
а не к отдельному примеру.

После явного одобрения выполняется полный запуск через общий launcher по
сохранённому локальному составу задач, без повторного inventory. Успешный
apply и readback переводят карточку в `Готово`; любой fail-closed или ошибка —
в `Есть проблемы`. Исправление и новый dry-run снова возвращают её на проверку.

У тестового прогона три области одного общего launcher: только родитель, один
случайный ребёнок и вся группа. Выбранный случайный ребёнок фиксируется в
локальном состоянии запуска. Прогоны выполняются последовательно, не содержат
`--apply` и по завершении сохраняют превью в локальный кеш.

## API первого среза

```text
GET   /api/groups
GET   /api/groups/{group_key}
GET   /api/groups/{group_key}/preview
POST  /api/groups/{group_key}/preview
GET   /api/groups/{group_key}/dry-run
POST  /api/groups/{group_key}/dry-run
GET   /api/groups/{group_key}/inventory
POST  /api/groups/{group_key}/initialize
PATCH /api/groups/{group_key}
GET   /api/groups/{group_key}/comments
POST  /api/groups/{group_key}/comments
POST  /api/groups
POST  /api/sync
```

`PATCH` меняет только ручные поля. `initialize` выполняет разовый MCP-read и
обновляет локальный индекс. `dry-run` запускает общий launcher без `--apply` и
ничего не записывает по MCP. Будущий endpoint применения должен быть отделён
от них явно и завершаться обязательным readback.

## Срезы реализации

Уже реализованная основа включает:

- Preact-доска на основе минимальной части OpenKanban;
- Python API и SQLite;
- бэкфилл профилей и истории запусков;
- фильтр, перемещение карточек и широкая боковая панель;
- локальные комментарии и сохранение ссылки на Codex-задачу;
- реальные кэшированные превью одной или нескольких задач; если кэша нет,
  показывается честное пустое состояние без моковых данных.

Реализованный срез включает таблицы локального индекса, колонку
`Инициализация`, backend Initialize, вкладку `Все задачи` и чтение SQLite общим
launcher через `--inventory-db`. Следующими отдельными этапами остаются
создание/привязка Codex-задач и явное применение с MCP-readback.

## Ошибки и сохранность

- Один плохой отчёт не блокирует остальные карточки.
- Ошибка инициализации остаётся в `Инициализации`, ошибка локального dry-run не
  перемещает карточку, а `Проблемы` означает ошибку apply или MCP-readback.
- Переинициализация выполняется только отдельной командой пользователя.
- SQLite создаётся только под `var/` и не коммитится.
- Синхронизация идемпотентна.
- Ручные данные не удаляются при исчезновении профиля или run-каталога.
- API возвращает структурированную ошибку, а фронтенд показывает её внутри
  соответствующей панели без падения всей доски.

## Проверка

- Python-тесты проверяют объединение профилей и run-отчётов, выбор свежего
  отчёта, начальную колонку и сохранение ручной надстройки.
- Фронтенд-тесты проверяют фильтрацию по UUID и API-запрос регистрации.
- Один интеграционный тест запускает локальную API на временной SQLite и
  проверяет полный путь `sync -> list -> patch -> comment`.
- Ручная визуальная проверка подтверждает горизонтальный канбан и сравнение
  `родитель -> результат` в боковой панели на узком и широком окне.
